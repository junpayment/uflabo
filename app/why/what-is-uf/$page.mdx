## 主張: パースは 1 回でいい

React は Flow で書かれています。そして Flow は近年、React を記述するための構文を増やしてきました。`component` 宣言、`hook` 宣言、render 型、パターンマッチ、enum。これらを持つ型システムは他にありません。

ところが、それを使うには次のような作業が必要でした。

1. Babel を入れ、Flow プリセットと構文プラグインを設定する
2. React Compiler のプラグインを追加する
3. バンドラに同じ構文を教える
4. テストランナーに同じ構文を教える
5. リンタに同じ構文を教える
6. フォーマッタに同じ構文を教える

これが 4〜6 個の設定ファイルになります。「もっとも表現力の高い React の書き方が、もっとも準備の面倒な書き方になっている」というのが公式ドキュメントの言い方です。**uf はこの税金の除去であり、それ以外ではない**、と。

2 つのツールが「`component` とは何か」について合意しなければならない瞬間、その 2 つは合意するように設定されなければならず、そして合意しないように設定されることもできます。しかも静かに。テストは通るのにビルドは失敗する、フォーマッタが整形した構文をリンタが拒否する、という形で。

uf の答えは、**Meta 製の Flow パーサーそのものを 1 つのバイナリにコンパイルし、dev サーバー・本番ビルド・テストランナー・フォーマッタ・リンタがすべて同じ 1 本の構文木を読む**ことです。`uf.config.js` が唯一の設定ファイルで、それが Flow で書かれているのも同じ理由です。「型システムの設定は、その型システムでチェックされるべき」だからです。

## 代償: 正直に書かれている

公式ドキュメントが繰り返し強調するのは、**負ける行を同じ表に載せる**ことです。

- **エコシステムは TypeScript のもの。** npm のほとんどは `.d.ts` を出荷し、Flow の libdef は出荷しません。uf は TypeScript 宣言を Flow に翻訳しますが、翻訳できない箇所は `any` になります。
- **エディタ支援は薄い。** `uf lsp` はありますが、リネームも定義ジャンプも参照検索もありません。型エラーはターミナルの `uf check` で見ます。
- **知っている人が少ない。** 採用、Stack Overflow、「次のコントリビュータが `renders` を見たことがある確率」。すべて TypeScript 側に傾いています。
- **デプロイ実績がない。** 7 種類のアダプタと `--compile` は実装済みですが、uf 自身のパイプラインで実際の Cloudflare / AWS / コンテナに載せた実績はまだありません。
- **3 年の歴史がない。** プレリリースであり、安定性の保証はありません。

uf はこれらで勝つとは主張しません。主張するのは、「React を書いているのであって、JavaScript を React 付きで書いているのではない」なら、Flow は他の何にも言えないことを言えるし、その間に立っていたのはツールチェーンだけだった、ということです。

## どう決めるか（要約）

公式の [Flow と TypeScript](/uflabo/why/flow-vs-typescript) の結論をそのまま引くと:

- **TypeScript に留まるべき人**: 型付き依存が多くて `any` の穴を許容できない、チームが採用中、[負ける行](/uflabo/why/compare#負ける行を先に読む)のどれかが今期の生命線。「それはほとんどの人であり、妥当な答えだ」と公式も書いています。
- **uf を試すべき人**: 型システムに捕まえてほしいのが「足りない prop」「間違った場所から呼ばれた hook」「そこに属さない子コンポーネント」「拡張し忘れた match」であり、インターフェースが予告なく変わるプレリリースを許容できる人。
