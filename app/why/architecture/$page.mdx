## create-react-app の何がまずかったか

CRA は悪いツールではありませんでした。2016 年には正しい設計で、React アプリが必要とするようになったものに追いつけなかっただけです。そしてその失敗の仕方は、uf がどう失敗し得るかの仕様書に近い。

**第 1 の失敗: eject の崖。** `react-scripts` は webpack、Babel、ESLint、Jest、PostCSS を 1 つの依存の裏に隠しました。それが魅力のすべてで、機能しました。想定外の webpack プラグインが 1 つ必要になるまでは。そのとき唯一の道は `eject` で、隠されていた設定全体をリポジトリに書き出し、元に戻せませんでした。

**第 2 の失敗: 構造的なもの。** エコシステムのすべてのアップグレードが 1 つのパッケージを通らなければならなかった。

```
ecosystem change  →  react-scripts  →  you
```

推移的依存の脆弱性は、それを更新しても直せない。`react-scripts` のリリースを待つ。1 つのパッケージが、含むすべてのアップグレード経路を直列化しました。

**第 3 の失敗: ビルドを解決して止まった。** ルーティング、データフェッチ、コード分割は 3 つの問題ではなく 1 つでした。ルートのデータを知るルーターは、コードとデータを並行して取得できます。CRA はそれらを統合できず、すべての本番アプリが CRA の上に自前フレームワークを組みました。それこそ CRA が取り除くために存在した問題です。

一行の教訓: **合成可能性のない抽象は、やがてボトルネックになる。**

## uf の立ち位置

**uf はオーケストレーションを所有し、実装を所有しない。** 何が、いつ動き、部品がどう繋がるかを決めます。バンドラも、dev サーバーも、フォーマッタも、ランタイムも所有しません。

> 統合されたインターフェース、連合された実装。

これらは別のもので、一致しなければならないと仮定することが、統合ツールをモノリスに変えます。`uf dev` `uf build` `uf test` はオールインワンの体験ですが、その下では Vite は Vite で、Flow パーサーは Meta のものです。

これは目標であり、uf は今日それを満たしていません。フォーマッタとテストランナーは uf 自身のものです。Flow 対応のものがどちらも存在しなかったので意図的な選択ですが、原則の改訂ではなく例外であり、下の監査もそう扱います。**例外は、置き換え可能であり続けることで例外のままでいられる。**

## レッドライン

1. 避けられない場合を除き、Vite や Rolldown の挙動をフォークしない
2. アップストリームツールの設定スキーマを丸ごと鏡写しにしない
3. すべての組み込みプロバイダは置き換え可能でなければならない
4. eject コマンドを持たない
5. エコシステムの依存バージョンを単一パッケージが支配しない
6. コアは特定の JavaScript ランタイムに依存してはならない
7. すべてのオーケストレーションは inspect 可能でなければならない
8. プロバイダ固有の機能には到達可能なままでなければならない
9. デフォルトは便宜であり、アーキテクチャ上の要件ではない
10. uf のコアはグラフを所有し、ツールを所有しない

### eject を置き換える連続体

```
convention  →  configuration  →  provider replacement  →  raw provider API
```

各段階は前より小さな決定で、どれも後ろで閉まる扉ではありません。

### 3 つのランタイム

「ランタイム」は 3 つの問いで、それらを潰すことがツールチェーンが新しいターゲットを狙えなくなる原因です。

| | |
| --- | --- |
| オーケストレーションホスト | uf 自身が動く場所。ネイティブバイナリ |
| プラグインランタイム | JavaScript プラグインが動く場所。Node.js / Bun / Deno |
| ターゲットランタイム | 出力が動く場所。ブラウザ、ワーカー、サーバー |

## 性能もアーキテクチャの一部

uf の性能の約束は、ホームページの一文ではなく**失敗するテスト**として書かれています。ユーザーが体感するほど重要な経路には、逸脱したとき赤くなるフィクスチャと予算が必要です。

| 対象 | 守るべきこと | 証拠の場所 |
| --- | --- | --- |
| uf check | 推論・モジュール解決・クロージャ走査が「同じ作業の再発見」に比例してアロケートしない | `crates/uf_check/tests/allocation_budget.rs` など |
| uf lint | フレームワークルールは共有パースとルート知識の上で動き、同じプロジェクトを別途走査しない | `crates/uf_lint/tests/allocation_budget.rs` |
| uf test | Rust が探索・スケジューリング・タイムアウト・レポートを所有し、ホストがテスト本体を実行する | Testing と `packages/test` |
| フレームワーク | ルーター、RSC、Server Actions、ミドルウェアは孤立したヘルパーではなく 1 つのアプリグラフとしてテストされる | Routing など |
| UI | 公開 API は挙動・アクセシビリティ・スタイリングの自由。render のエスケープハッチは id・ハンドラ・ref・Flow 制約を保つ | `packages/ui/ui.test.js` |

予算が失敗したら、数字より先にアーキテクチャの失敗として読む。同じフィクスチャがより多くアロケートするなら、たいていキャッシュが共有されなくなったことを意味します。

## まだ守れていない箇所

監査のないルール一覧は飾りです。

- **Vite のスキーマの鏡写し（2）、半分閉じた。** `vite` キーは uf の生成物の上にマージされるので、uf が聞いたことのない Vite オプションにも届きます。残り: `dev` と `build` が依然 Vite のオプションを 1 つずつ再宣言している。
- **置き換え可能性（3）、1 プロバイダで達成。** `fmt.nonFlow.formatter` が JSON / CSS / TypeScript を誰がフォーマットするか（Biome、Prettier、なし）を選ぶ。lint エンジン、フォーマッタのパーサー、タスクランナー、パッケージリゾルバは依然 1 変種のみ。
- **ロックステップのバージョン（5）。** すべての `@uniflowed/*` が兄弟を exact に固定し、1 つのスクリプトが全部を設定する。パッケージが 1 つのものである間は正しいが、関所の始まりでもある。1.0 前にアダプタは独立して動く必要がある。
- **inspect 可能性（7）、達成。** `uf inspect --json` と `uf explain <command>`。
- **uf が 2 つのツールを所有する（10）。** フォーマッタとテストランナー。置き換え可能であり続けなければ、このページの主題そのものになる。

### 開いた線をどう閉じるか

| 線 | 閉じる条件 |
| --- | --- |
| 2 — Vite のスキーマ | 唯一の消費者が `viteConfig()` である設定キーがあればテストが失敗する |
| 3 — 置き換え可能性 | `fmt.nonFlow.formatter` は完了。lint エンジン、フォーマッタパーサー、タスクランナー、パッケージリゾルバがそれぞれ 1 変種のまま |
| 5 — ロックステップ | 兄弟依存が範囲になり、1 パッケージを他と独立にリリースできる |
| 10 — 所有する 2 ツール | `uf fmt` と `uf test` がバンドラと同じ継ぎ目を通って解決される |

## 検討対象外

どれも合理的に聞こえ、どれもこのページの主題への一歩です。

- どんな綴りであれ eject コマンド。「有効な Vite 設定を印字してコピーできるフラグ」も、実際には eject になる。
- Flow がすでに名付けたものへの uf 流の名前。
- プロバイダを合わせるためのベンダリング。アップストリームかプラグイン、決してフォークではない。

## レッドラインが防がない失敗

CRA の第 3 の失敗はアーキテクチャの問題ではありませんでした。ビルドを解決して止まり、全員がその上に自前フレームワークを組んだ。

上のどれもそれを防ぎません。防ぐのは、uf がツールチェーンであると同時にフレームワークであること（ルーター、RSC グラフ、Server Actions、データ層）であり、それらが「統合ポイントとしてドキュメントに書かれる」のではなく「uf が出荷する答え」であることです。監査は「ボトルネックにならないこと」について、こちらは「使う価値があること」についてです。

全記録と論拠は `docs/red-lines.md` にあります。
